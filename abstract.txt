# VeloShield: An Authorized Web Security Assessment, Load Resilience, and Mitigation Recommendation Platform

**Architecture:** Decoupled Cloud Web Architecture  
**Frontend:** Vercel  
**Backend:** Render  
**Database:** Neon Serverless PostgreSQL  
**Backend Runtime:** Java 21 with Embedded Apache Tomcat  
**Technology Stack:** HTML5, CSS3, Modern JavaScript (ES6+), Java Servlets, AJAX, JDBC, HTTP, HTTP Session Management, Cookie Storage, Maven, PostgreSQL, ExecutorService, and REST-style APIs

## 1. Executive Summary

VeloShield is a web-based security assessment and application resilience platform designed to help website administrators evaluate the security and performance behavior of their authorized web applications under controlled testing conditions. The platform combines domain ownership verification, bounded concurrent HTTP testing, real-time performance monitoring, historical assessment storage, and defensive mitigation recommendations within a single web-based dashboard.

Unlike conventional monitoring applications that primarily observe system behavior after deployment, VeloShield provides an active and controlled assessment workflow. Administrators can verify ownership of a target domain, configure predefined testing limits, execute controlled concurrent requests, monitor response behavior, analyze performance degradation, and obtain defensive configuration recommendations based on the observed results.

The platform follows an authorization-first methodology. Active assessments are permitted only for domains that have successfully completed the ownership verification process. This design helps ensure that the platform is used for legitimate security testing and resilience evaluation rather than unauthorized traffic generation.

## 2. Technical Problem

Modern web applications must remain available and responsive while handling changing traffic volumes, concurrent requests, network delays, and application-layer security threats. Insufficient load testing and limited performance visibility can make it difficult for administrators to determine how an application behaves when traffic increases.

Traditional monitoring systems generally focus on observing production behavior, while separate security and load-testing utilities may require multiple tools and workflows. There is therefore a need for an integrated platform that can perform authorized assessments, collect measurable performance information, preserve historical results, and assist administrators in developing appropriate defensive configurations.

VeloShield addresses this requirement through a decoupled frontend-backend architecture supported by Java Servlets, JDBC, PostgreSQL, asynchronous browser communication, and controlled multithreaded request execution.

## 3. System Architecture

VeloShield follows a three-layer cloud deployment architecture.

### Frontend — Vercel

The frontend is developed using HTML5, CSS3, and modern JavaScript. It provides the administrator dashboard for authentication, domain registration, verification, assessment configuration, live result monitoring, historical test analysis, and mitigation recommendation generation.

AJAX and asynchronous JavaScript requests communicate with backend REST-style servlet endpoints without requiring complete page reloads.

### Backend — Render

The backend is implemented using Java Servlets and Java 21. Maven manages the application dependencies and build process.

Apache Tomcat is included directly through Maven as an **embedded Tomcat runtime**. Therefore, the project does not require a separately installed or externally managed Tomcat server.

The application starts the embedded Tomcat server from the Java `Main` class and exposes the servlet-based API endpoints required by the frontend.

The backend is deployed directly as a Java application/JAR on the hosting environment without using Docker.

### Database — Neon Serverless PostgreSQL

Neon Serverless PostgreSQL provides persistent storage for user accounts, verified targets, assessment configurations, execution statistics, and historical test results.

JDBC is used by the Java backend to communicate with PostgreSQL.

## 4. Core Methodology

### 4.1 Authorization and Domain Ownership Verification

Before an assessment can be performed, the administrator registers a website origin with VeloShield.

The system generates a unique verification token. The administrator places the token inside a predefined verification file on the target domain.

For example:

```text
/.well-known/veloshield-verification.txt
```

The file contains a unique value such as:

```text
veloshield=GENERATED_TOKEN
```

VeloShield then retrieves the verification resource and compares the returned token with the token stored in the database.

Only successfully verified domains can be selected for active assessment.

This authorization mechanism establishes an ownership-control workflow and prevents ordinary users from directly entering arbitrary targets for testing.

### 4.2 Controlled Concurrent Load Assessment

VeloShield uses Java's `ExecutorService` and bounded thread pools to execute controlled concurrent HTTP requests against verified targets.

Administrators configure parameters such as:

- Target domain
- Concurrency level
- Assessment duration
- Maximum request count

The backend enforces predefined safety limits on these values.

During the assessment, the system collects measurable performance information including:

- Total attempted requests
- Successful requests
- Failed requests
- HTTP response status codes
- Average response latency
- p95 response latency
- Network or timeout errors
- Assessment duration

The system does not automatically interpret a single HTTP error such as `502` or `504` as proof of a particular infrastructure failure. Instead, the observed response and performance metrics are recorded as evidence for further analysis.

### 4.3 Multithreaded Request Processing

The backend uses Java's `ExecutorService` to manage concurrent request execution.

Instead of creating an unrestricted operating-system thread for every request, VeloShield uses a bounded worker pool.

The general processing model is:

```text
Administrator
      ↓
Assessment Configuration
      ↓
Backend Validation
      ↓
Verified Target Check
      ↓
Bounded ExecutorService
      ↓
Concurrent HTTP Requests
      ↓
Metric Collection
      ↓
Database Storage
      ↓
Dashboard Visualization
```

This demonstrates practical use of Java concurrency and asynchronous server-side processing.

### 4.4 Real-Time Performance Monitoring

The frontend periodically communicates with backend API endpoints using AJAX.

The backend provides JSON-based assessment information that can be displayed in the dashboard without requiring a complete page refresh.

The dashboard can display:

- Assessment status
- Number of requests
- Successful requests
- Failed requests
- Average response time
- p95 response time
- HTTP errors
- Assessment history

This provides administrators with a convenient view of application behavior during controlled testing.

### 4.5 Persistent Assessment History

Each assessment is stored in Neon PostgreSQL.

The database records information such as:

```text
Assessment ID
User ID
Target ID
Assessment Status
Concurrency
Duration
Maximum Requests
Attempted Requests
Successful Requests
Failed Requests
Average Latency
p95 Latency
Error Distribution
Start Time
Completion Time
```

This allows administrators to compare previous assessment runs and understand changes in application performance over time.

### 4.6 Automated Mitigation Recommendation

After an assessment, VeloShield can provide defensive configuration recommendations based on the observed assessment context.

The platform can generate templates for technologies such as:

- Nginx
- Cloudflare Web Application Firewall

For example, an Nginx recommendation may contain rate-limiting configuration.

The generated configuration is presented to the administrator for inspection and manual deployment.

VeloShield does **not automatically modify the target server or deploy firewall rules**.

This review-based approach reduces the possibility of accidentally blocking legitimate users or introducing unsuitable production configurations.

## 5. Authentication and Session Management

VeloShield provides administrator authentication using email and password credentials.

Passwords are stored as secure password hashes rather than plaintext values.

After successful authentication, the backend creates an HTTP session containing the authenticated user's identity.

A session cookie is used to associate subsequent requests with the authenticated session.

Protected API endpoints verify the session before allowing access to:

- Registered targets
- Assessment execution
- Assessment history
- Reports
- Mitigation recommendations

This demonstrates practical implementation of server-side HTTP session management and cookie-based authentication.
